# Веб-приложение для ПР №2 и ПР №4 (ОВС)

Минимальное веб-приложение на Python (`http.server`), которое можно
запускать несколькими идентичными экземплярами и балансировать между
ними.

- **ПР №2** — наглядно показывает, какая backend-нода ответила на запрос.
- **ПР №4** — пишет в отказоустойчивый кластер PostgreSQL
  (Patroni + etcd) и читает из него **только через HAProxy**, переживает
  переключение primary и показывает, какой узел БД обслужил запрос.

Веб-часть использует только стандартную библиотеку. Для работы с
PostgreSQL нужен драйвер `psycopg2` (`requirements.txt`). Без драйвера
или без `PG_WRITE_HOST` приложение работает как в ПР №2, а эндпоинты БД
отвечают `503`.

## Запуск

```bash
pip install -r requirements.txt   # только для функций БД
python app.py
```

Подробная инструкция — в [RUNNING.md](RUNNING.md).

## Переменные окружения

Веб-часть:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `8080` | порт HTTP |
| `NODE_ID` | hostname | метка ноды в ответах |

Подключение к БД (адрес — **HAProxy**, не узел PostgreSQL):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PG_WRITE_HOST` | — (обязательна для БД) | адрес HAProxy, порт записи |
| `PG_WRITE_PORT` | `5000` | write-endpoint (только primary) |
| `PG_READ_HOST` | = `PG_WRITE_HOST` | адрес HAProxy, порт чтения |
| `PG_READ_PORT` | `5001` | read-endpoint (реплики) |
| `PG_DB` / `PG_USER` / `PG_PASSWORD` | `ovs` / `ovs_app` / пусто | БД и учётные данные |
| `PG_SSLMODE` | `verify-full` | режим TLS соединения с БД |
| `PG_SSLROOTCERT` | — | путь к сертификату CA |
| `PG_CONNECT_TIMEOUT` | `3` | таймаут подключения, сек |
| `PG_RETRY_SECONDS` | `30` | сколько повторять запрос при недоступности БД (failover) |
| `PG_RETRY_DELAY` | `1` | пауза между попытками, сек |

## Эндпоинты

- `GET /` — HTML-страница с указанием ноды, ответившей на запрос.
- `GET /api/info` — та же информация в JSON.
- `POST /api/write` — вставка строки в таблицу `ovs_log` через
  write-endpoint. Текст — в JSON `{"note": "..."}` или `?note=...`.
  Таблица создаётся автоматически (`CREATE TABLE IF NOT EXISTS`).
- `GET /api/read?limit=20` — последние строки и общее число записей
  через read-endpoint (реплики).
- `GET /dbz` — диагностика: к какому узлу и роли подключились write и
  read endpoint (`200`, если оба доступны, иначе `503`).
- `GET /healthz`, `GET /readyz` — проверки живости/готовности;
  **не зависят от БД**, чтобы сбой PostgreSQL не выводил веб-ноду из
  балансировки.

Ответы БД содержат блок `db`: `role` (`primary`/`replica`, по
`pg_is_in_recovery()`), `server_addr`, `server_port` и `ssl` (признак
шифрованного соединения из `pg_stat_ssl`), а также `attempts` и
`elapsed_seconds` — число попыток и время выполнения. Именно по ним
фиксируется смена primary и время восстановления при failover.
Каждый ответ также содержит заголовки `X-Node-Id` и `X-Hostname`.

Примеры:

```bash
curl -X POST -H 'Content-Type: application/json' \
     -d '{"note":"проверка"}' http://localhost:8080/api/write
curl http://localhost:8080/api/read?limit=5
curl http://localhost:8080/dbz
```

## Поведение при отказе узла БД

Соединение открывается на каждый запрос (долгоживущих соединений нет,
поэтому после падения primary «мёртвых» соединений не остаётся). При
`OperationalError`, обрыве соединения или попадании на узел в режиме
read-only запрос повторяется каждые `PG_RETRY_DELAY` секунд, но не
дольше `PG_RETRY_SECONDS`; затем возвращается `503`. Пока HAProxy не
увидит нового лидера через Patroni REST API, запись ждёт, а после
переключения проходит через тот же endpoint без изменения настроек.

Повтор записи при сбое в момент `COMMIT` теоретически может привести к
дубликату строки — для демонстрации это допустимо, а потерянные при
асинхронной репликации записи видны по пропускам `id`.

## Шифрование (п. 10 ПР №4)

- Приложение ↔ HAProxy ↔ PostgreSQL: `sslmode=verify-full` с проверкой
  сертификата по CA (`PG_SSLROOTCERT`); HAProxy работает в
  `mode tcp` и пропускает TLS PostgreSQL насквозь. Имя в
  `PG_WRITE_HOST` должно совпадать с SAN сертификата.
- Клиент ↔ веб-приложение: HTTPS на Apache/Nginx (само приложение TLS
  не терминирует).
- etcd, Patroni REST API и репликация PostgreSQL настраиваются на TLS
  на стороне инфраструктуры (вне приложения).

## Соответствие ограничениям ПР №2

1. **Идентификация backend-узла.** `/`, `/api/info` и заголовки
   `X-Node-Id`/`X-Hostname` показывают, какая нода обработала запрос.
2. **Без TLS в самом приложении.** Терминация HTTPS — на Apache/Nginx.
3. **Без пользовательских сессий.** Логин, корзины, cookie не
   реализуются и нигде не хранятся.

(В ПР №2 приложение не использовало БД; начиная с ПР №4 состояние
хранится только в кластере PostgreSQL, сама нода остаётся stateless.)

## Потребление ресурсов

Один инстанс потребляет порядка 15–25 МБ RSS (+ драйвер `psycopg2`) и
запускается почти мгновенно.
